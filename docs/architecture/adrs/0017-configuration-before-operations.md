# ADR-0017: Configuration Before Operations, and Plan as a First-Class Entity

- **Status:** Accepted
- **Date:** 2026-07-27
- **Related:** [vision.md](../vision.md), [feature-map.md — Billing](../feature-map.md#billing), [feature-map.md — cross-cutting principle note](../feature-map.md), [roadmap.md](../roadmap.md), [pricing-strategy.md](../pricing-strategy.md) design principle 5, [product-principles.md](../product-principles.md) principle 14, [domain-model.md](../domain-model.md), [ADR-0009](./0009-regional-payment-methods-first-class.md), [ADR-0011](./0011-narrower-access-for-sensitive-modules.md), [ADR-0012](./0012-enrollment-historized-not-mutable-status.md), [ADR-0013](./0013-soft-delete-universal-default.md)

## Context

Nursery OS's Billing & Payments module shipped with invoices created and priced entirely by hand — a person selects a child, a guardian, and types in line items every time, every month, for every family. This was a reasonable place for an MVP to start: it beat having no billing frontend at all, and it followed the same "something real and manual beats nothing" logic already governing this product's build sequence (see [ADR-0015](./0015-backend-complete-modules-prioritized-for-frontend.md)).

But `vision.md` already positions Nursery OS as "one connected operating system," not a record-keeping tool with a billing tab bolted on. A system that requires a human to re-decide the same fee, the same discount, and the same schedule by hand every single cycle is not, in any meaningful sense, an operating system — it is a ledger with a nicer UI. Two rounds of dedicated product-strategy work (a UX audit, a persona-level Experience Strategy, and a Product Identity exercise) converged on the same conclusion: what should make this product feel different from Brightwheel, Procare, Illumine, and Lillio isn't just regional payment methods or Arabic-first UI — it's that the nursery configures how it runs once, and daily operations become the automatic, mechanical consequence of that configuration, not a fresh manual decision every time.

That conclusion was then stress-tested twice before being adopted: once as a full ERP-style business-process design covering eighteen distinct operational areas (Classes, Plans, Fees, Billing cycles, Discounts, Waivers, Attendance validation, and the full child lifecycle), and once as an adversarial review of that same design against real nursery edge cases and how mature ERPs (SAP, Odoo, Dynamics, ERPNext) handle the same problems. This ADR formalizes what survived both passes.

## Problem

Two related but distinct problems needed solving:

1. **What is the product's operating philosophy for recurring business rules?** Without an explicit answer, every future module (Attendance rules, working hours, holidays) risks re-deriving its own ad hoc answer to "does this get configured once or re-entered every time," producing an inconsistent product.
2. **What does `Plan` actually mean, architecturally?** The Product Identity work had already named `Plan` as a first-class entity in prose, but "first-class entity" is not a data model. Without a decision, the natural failure mode is treating a Plan as a single monolithic bundle of schedule and price — which the ERP-style workflow review demonstrated leads directly to plan-explosion the moment any real customization (meals, transport, a negotiated rate) is needed.

## Decision

**Configuration is the default. Manual overrides are the exception, not the normal workflow.** A nursery configures its business — classes, plans, fees, billing cycles, discounts, sibling rules, waivers, accepted payment methods, attendance rules, working hours, and holidays — before it starts operating. Daily operations (an invoice generating, an attendance check-in validating against a schedule, a sibling discount applying) are then the mechanical consequence of that configuration. This does not mean manual operations disappear: the recurring case runs itself; a human's attention is reserved for the genuine exception (a field trip, a hardship waiver, a one-time charge) — never the routine case.

**`Plan` is a first-class entity, decomposed rather than monolithic.** A `Plan` (Full Time, Half Time, Part Time, Daily) carries a billing cycle and a permitted attendance schedule. It does **not** carry a single fixed price inline — price is its own historized sub-entity (`PlanPrice`), so a price change never silently reprices an already-enrolled family. It does **not** bundle every possible add-on into itself — optional and mandatory charges (meals, transportation, registration) are separate `Fee`s attached via a `Plan`↔`Fee` join, individually toggle-able per child, specifically to avoid a combinatorial explosion of near-duplicate Plans ("Full Time + Meals," "Full Time no Meals," "Full Time + Transport"...) as the nursery's offerings grow.

This decision, and the roughly twenty supporting rules it implies (deposits and withdrawal notice periods, capacity validation on plan changes, explicit non-recurring holiday dates, a floor-at-zero rule on discount stacking, tiered sibling discounts, idempotent invoice generation, oldest-invoice-first payment allocation across a guardian's full family, and a unified `ManualOverride` audit mechanism instead of a bespoke exception path per feature) are recorded in full, with their business rationale, in [domain-model.md](../domain-model.md)'s Configuration Engine extension. This ADR records *why* those rules exist as one coherent decision; the domain model records *what* they are as entities and constraints.

## Alternatives considered

1. **Keep billing entirely manual, indefinitely, as a permanent product choice.** Rejected: this was defensible as a temporary MVP simplification, not as a permanent identity. It directly contradicts the product's own "operating system, not record-keeping software" positioning, and it doesn't scale past a handful of children before becoming the single biggest source of owner busywork the product otherwise claims to eliminate.
2. **Configuration only at Professional tier and above, keep Starter fully manual.** Rejected explicitly during the Product Identity work: `pricing-strategy.md` design principle 2 already commits to "every plan must feel complete for its target customer, not artificially crippled." Gating the *operating philosophy* itself behind a paywall — not just its depth or automation — would mean a Starter-tier owner learns a fundamentally different way of running their nursery than the one they'd use after upgrading. Tiers differ in depth and automation (Starter: basic Classes → Plans → Fees; Professional: the full discount/waiver engine, recurring automation, late-fee automation), never in whether configuration exists at all.
3. **A single monolithic `Plan` bundling schedule, price, and every add-on.** Rejected after the ERP-style workflow review specifically identified plan-explosion as the predictable failure mode — any real customization need (a family that wants the schedule but not the meals) forces a new near-duplicate Plan variant, and the number of Plans a nursery must maintain grows combinatorially with its offerings rather than staying proportional to genuinely distinct schedules.
4. **Full maker-checker (dual authorization) on financially significant manual overrides, matching large-ERP norms (SAP, Dynamics).** Rejected deliberately, not overlooked: this pattern is correct for an organization with a real approval hierarchy, and actively unworkable for this product's actual target — a Starter or Professional-tier nursery where `OWNER` and `ADMIN` are frequently the same one or two people. Requiring a second approver who doesn't exist would block legitimate work, not protect against misuse.
5. **Payment clearing/settlement-status tracking (recorded vs. confirmed-cleared), matching mature AR modules.** Rejected for the same reason: real complexity that exists in large ERPs for a reason, and genuine over-engineering for a manual-recording, cash/wallet/bank-transfer-dominant market where the owner is not reconciling against automated bank feeds. Revisit only once automated bank reconciliation (already Enterprise-tier elsewhere in the Bible) is actually being built.
6. **Auto-recurring annual holiday dates (a fixed Gregorian date repeating every year).** Rejected specifically because it is wrong for this product's own core market: Islamic calendar holidays (Eid al-Fitr, Eid al-Adha) shift roughly eleven days earlier every Gregorian year, so a fixed-date recurrence rule would silently drift incorrect within a single year — directly undermining the regional-first positioning [ADR-0009](./0009-regional-payment-methods-first-class.md) and [ADR-0010](./0010-arabic-rtl-foundational-not-bolted-on.md) already commit this product to elsewhere.
7. **A `Guardian`-per-child-group billing relationship instead of `Guardian` acting directly as the billing account.** Considered during a dedicated pre-commit maintainability review of this design and rejected for now: the domain model already carries a deferred `BillingAccount`/`BillingAccountGuardian` entity for exactly the case this would solve (multiple guardians sharing financial responsibility, e.g. shared custody), and building a second, competing billing-grouping concept alongside an already-planned one would be redundant. `Guardian` acts as the de facto billing account in the interim, with the known, accepted gap (children of two separately-billed guardians in one household aren't recognized as siblings) and an explicit migration note on `BillingAccount`'s own deferred-entity rationale naming exactly what moves onto it later.

## Consequences

**Positive:**
- Gives the product a single, consistent answer to "does this get configured once or re-decided every time" that future modules (working hours, holidays, attendance rules) can extend rather than each inventing their own convention — [feature-map.md](../feature-map.md)'s new cross-cutting principle note names this explicitly.
- `Plan` decomposition (base plan + separable `Fee`s, historized `PlanPrice`) is the same shape mature subscription-billing engines (Zuora, Chargebee, Odoo Subscriptions) converge on for the same reason: it keeps plan count proportional to genuinely distinct offerings, not every possible combination of add-ons.
- The unified `ManualOverride` mechanism (one audit trail, one authorization tier, one reason-code discipline for every exception — waivers, one-time charges, out-of-schedule attendance charges, immediate plan changes) directly reuses the exact discipline already proven for Attendance corrections, rather than inventing a bespoke exception path per feature.
- Every business rule in this decision was stress-tested against real ERP precedent (what SAP/Odoo/Dynamics/ERPNext actually do) before being adopted, and several large-ERP patterns were explicitly rejected as wrong-sized for this product rather than reflexively copied — this decision is deliberately calibrated to the target market, not maximalist.

**Trade-offs accepted:**
- None of this exists yet. No `Plan`, `PlanPrice`, `Fee`, `Discount`, `Waiver`, `Holiday`, `BillingRun`, `PaymentAllocation`, or `ManualOverride` entity exists in the implemented schema; Billing's shipped shape remains entirely manual line-item entry. This ADR and the domain-model extension it references describe the target architecture the roadmap now commits to building toward sooner ([roadmap.md](../roadmap.md) Phase 1), not a claim about current implementation.
- `Payment`'s data shape changes materially — from a strict one-to-one relationship with `Invoice` to a many-to-many relationship via `PaymentAllocation`, anchored to `Guardian` as the billing party. This is a real migration cost against the already-shipped `Payment` model, accepted because the alternative (no way to represent a lump-sum payment across multiple invoices, or an overpayment functioning as credit) is a genuine gap the adversarial review surfaced in what's live today.
- Several real gaps the review identified — `Classroom` age-band/staff-ratio fields, per-service working-hours windows with a pickup grace period, a quantity dimension and tax-category field on `Fee` — were deliberately left out of this pass. They are recorded in [domain-model.md](../domain-model.md)'s deferred-entities table with the same "cheap addition later, not a redesign" reasoning applied to every other deferral in that table, not silently dropped.
- A dedicated pre-commit maintainability review of this same design, run before implementation authorization, found and corrected several real gaps rather than only validating what was already written: `InvoiceLineItem` had no explicit pointer back to the `PlanPrice` version that generated a tuition charge; `ManualOverride` was missing `previousValue`/`newValue`, leaving its audit trail unable to show what actually changed; and `CreditNote` — the B7 Refunds & Credits construct, already accepted in the earlier adversarial review — had been described in prose but never actually added as an entity. All three are fixed in [domain-model.md](../domain-model.md) as of this ADR's current version; none required reopening the underlying Configuration Before Operations decision itself.
- The Suspension seat-hold-vs-release question is *partially* deferred: V1 ships one fixed behavior (seat held, billing paused, attendance excluded from the default roster but never technically blocked) rather than a tenant-configurable policy, even though a configurable version is understood to be the eventual correct shape. The domain model deliberately isolates this behavior behind a single centralized capacity-counting rule specifically so that future configurability is a one-place change, not a redesign — an explicit extensibility commitment, not just a deferral.
- A final pre-commit pass, run explicitly as a 10-year chief-architect challenge plus a code-review-isolation lens, found one structurally significant gap and several smaller ones. **`Enrollment` was carrying two unrelated concerns in one table** — placement (child, classroom, status, dates) and billing terms (`plan_id`, `billing_guardian_id`, custom rate, deposit, withdrawal notice) — which two independent arguments converged on fixing the same way: a bounded-context lens (Placement/Operations vs. Billing/Finance shouldn't share one entity even though their lifecycle is coupled) and a PR-isolation lens (a future operations-only change and a future billing-only change would otherwise compete for review on the same table, the same migration, the same merge conflicts). Fixed by splitting into `Enrollment` + a new 1:1 `EnrollmentBillingTerms`, created and closed together, never independently — see [domain-model.md](../domain-model.md)'s Entity Reference and Soft-delete cascade policy sections. This is the kind of split that is cheap now and expensive later specifically *because* `Enrollment` is one of the two tables in this whole system too structurally important to retrofit after real data and real integrations exist — the same reasoning [ADR-0012](./0012-enrollment-historized-not-mutable-status.md) already applied to keep `Enrollment` historized instead of a mutable status field.
- The same pass added sequential human-readable document numbering (`Invoice.invoiceNumber`, `CreditNote.creditNoteNumber`) — flagged specifically because it is the one change in this whole review that touches already-live data (existing `Invoice` rows need a backfilled number, not just new ones going forward) rather than a purely additive design-only change like everything else in the Configuration Engine extension. It also standardized `decimal(12,2)` across every monetary field in the document (closing a quiet rounding-drift risk found by comparing precision across tables) and made `BillingRun` execution an explicitly staggered, queued-per-tenant job rather than a naive same-moment-for-everyone batch, after naming the thundering-herd failure mode that a synchronous day-1-of-the-month batch would produce at real platform scale.
- From the code-review-isolation lens specifically: several invariants in this design (centralized capacity counting, idempotent `BillingRun` regeneration, the discount/waiver floor-at-zero) are business rules no schema constraint can fully enforce, which means their correctness depends on staying centralized in shared service functions rather than getting reintroduced inline by a future well-intentioned, individually-reasonable small PR. This is now called out directly in [domain-model.md](../domain-model.md)'s business invariants section as implementation-phase guidance, not left as an assumption reviewers are expected to remember unprompted.

- A final fresh-eyes read before commit resolved three remaining ambiguities, all documentation-only — no entity or relationship changed shape as a result. **`SiblingDiscountTier`'s position in the `Discount`/`Waiver` stacking order was undefined**; it's now explicit that it always adds to whatever stackable-plus-winning-exclusive `Discount` combination already applies, rather than competing with it, and is applied before `Waiver` like every other discount. **The deposit lifecycle (`EnrollmentBillingTerms.depositAmount`/`depositRefundPolicy`) had no mapping onto `InvoiceLineItem`/`CreditNote`**; it now reuses existing mechanisms end to end with no new fields — collection via an ordinary `ONE_TIME_CHARGE` (`chargeCategory = OTHER`, described in `description`), forfeiture and apply-to-final needing no new record at all (the latter is just ordinary unallocated-credit allocation), and an actual refund via `CreditNote` with `reasonCode = OTHER` plus a note. A dedicated code for either was considered and deliberately deferred — nothing queries or reports on deposits distinctly yet, so a dedicated value would exist for a use case that doesn't exist; adding one later is a purely additive change once real reporting need shows up. **`BillingRun`'s resolution behavior when a billing-terms or price change lands after a period's `DRAFT` invoice already exists was implicit**; it's now stated explicitly as period-overlap resolution (never "whichever record is currently open"), paired with an explicit default — billing-terms changes take effect next cycle, a mid-cycle change is only possible through the existing `PLAN_CHANGE_IMMEDIATE` override — that deliberately keeps `BillingRun` free of any automatic proration engine. Proration, when actually wanted, follows the same manual `CreditNote`/one-time-adjustment pattern `WITHDRAWAL_PRORATION` already established, never automatic multi-segment math.
- A `BillingRunEvent` audit-trail entity (who/when/why triggered a regeneration) was drafted and then deliberately removed before commit, not deferred with a pre-built replacement. It would have been real, ongoing infrastructure — its own table, migration, and RLS policy, logging every routine run forever — for a traceability need nothing in the current product actually exercises yet. Recorded in the Architecture Backlog as: *if implementation later proves regeneration history is genuinely needed, introduce the smallest solution that solves the real, observed problem* — not rebuilt from this design speculatively.

- Any future configuration-before-operations instance (Attendance rules, working hours, holidays as tenant-configurable surfaces beyond the `Holiday` calendar entity itself) should follow the same decomposition discipline `Plan`/`Fee` establishes here: separate the stable, rarely-changing configuration from the thing that varies per assignment, rather than one growing monolithic entity per module.
- The next real decision this ADR anticipates but does not make is the Suspension seat-hold-vs-release **policy toggle** — building it is explicitly out of scope for the initial Configuration Engine implementation, but the capacity-counting rule it will eventually parameterize is being built as a single evaluation point now specifically so that decision doesn't require touching every query site later.
- `Fee.quantity` and `Fee.taxCategory`, `Classroom` age-band/ratio fields, and per-service working hours are named, reviewed, and explicitly not built in this pass — the next Configuration Engine milestone should treat [domain-model.md](../domain-model.md)'s deferred-entities table as the starting checklist, not rediscover these gaps from scratch.
- Implementing this design in `schema.prisma` is a separate, later task requiring its own migration plan and its own approval — this ADR and the domain-model extension are the approved *design*, not an implementation authorization.
